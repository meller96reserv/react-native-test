# Архитектура приложения

## 1. Контекст и цели

Приложение реализуется на React Native с Expo и TypeScript. Основной пользовательский путь:

```text
первый запуск → onboarding → paywall → эмуляция покупки → home
повторный запуск с подпиской ─────────────────────────────→ home
```

Приоритеты: предсказуемый запуск, простая модульная структура, доступный UI, отсутствие лишних
зависимостей и возможность без переделки заменить эмуляцию покупки реальным billing-сервисом.

## 2. Технологические решения

| Область            | Решение                                     | Причина                                                    |
| ------------------ | ------------------------------------------- | ---------------------------------------------------------- |
| Платформа          | Expo, managed workflow                      | быстрый запуск на Android/iOS, минимум нативной настройки  |
| Язык               | TypeScript strict                           | безопасные контракты состояния, тарифов и компонентов      |
| Навигация          | Expo Router                                 | файловые маршруты, типизированные ссылки, нативный stack   |
| Локальное хранение | `@react-native-async-storage/async-storage` | устойчивое key-value хранение между запусками              |
| Состояние          | React Context + `useReducer`                | состояние мало и глобально; внешний store был бы избыточен |
| Валидация          | узкий runtime parser хранимой записи        | AsyncStorage считается недоверенным источником             |
| Тесты              | Jest + React Native Testing Library         | проверка reducer, persistence и ключевых UI-сценариев      |
| Форматирование     | ESLint + Prettier                           | воспроизводимый quality gate                               |
| Игровые анимации   | Reanimated UI runtime                       | стабильные transforms без покадровых React-render          |
| Игровое аудио      | Expo Audio                                  | локальные эффекты и музыка с управлением жизненным циклом  |

Намеренно не добавляются сетевой клиент, backend-state библиотека, UI-фреймворк и FlashList:
в текущем ТЗ нет сети, сложного серверного состояния или длинного динамического списка.

## 3. Модульная структура

```text
app/                         # тонкий routing/composition слой Expo Router
  _layout.tsx
  index.tsx                  # стартовой redirect после hydration
  onboarding.tsx
  paywall.tsx
  home.tsx
src/
  components/                # переиспользуемые UI-компоненты
  features/
    onboarding/              # экран и локальные элементы onboarding
    paywall/                 # тарифы, экран, purchase use case
    home/                    # главный контент
      game/                  # runtime, engine, config, audio, record persistence
        components/          # HUD, сцена, фон, дорога и спрайты
  session/                   # session model, provider, hooks, reducer
  storage/                   # интерфейс и AsyncStorage-реализация
  theme/                     # цвета, spacing, typography, radius
  types/                     # общие типы только при реальной необходимости
  utils/                     # чистые общие функции
tests/                       # интеграционные сценарии при необходимости
```

Маршрутные файлы не содержат бизнес-логику: они импортируют feature screen. Feature-модули могут
зависеть от `components`, `session`, `theme` и `storage` через публичные контракты; общие слои не
зависят от features.

## 4. Модель состояния

Минимальная session-модель:

```ts
type SubscriptionPlan = 'monthly' | 'yearly';

type SessionState =
  | { status: 'hydrating' }
  | { status: 'anonymous'; onboardingCompleted: boolean }
  | { status: 'subscribed'; plan: SubscriptionPlan };
```

Дискриминируемое объединение исключает невозможные комбинации флагов. Provider отвечает за:

- однократную гидратацию при старте;
- завершение onboarding в памяти текущей сессии;
- эмуляцию покупки и атомарное сохранение результата;
- состояние выполнения покупки и понятную ошибку записи;
- предоставление небольшого стабильного API feature-слоям.

Onboarding отдельно сохранять необязательно по исходному ТЗ: до покупки новый запуск начинает
воронку заново. Сохраняется версия записи, выбранный план и факт активной эмулированной подписки.
Версия позволяет безопасно мигрировать формат позже.

## 5. Запуск и маршрутизация

Корневой layout монтирует `SessionProvider` и Stack. Пока идёт чтение AsyncStorage, показывается
стабильный launch/loading view, поэтому onboarding не мигает перед home. После hydration:

- `subscribed` → `/home`;
- `anonymous` без завершённого onboarding → `/onboarding`;
- завершён onboarding в текущей сессии → `/paywall`.

После успешной покупки используется `replace`, чтобы кнопка Back не возвращала пользователя к
paywall. Route guard также не позволяет вручную открыть home без подписки или paywall после неё.

## 6. Покупка и хранение

Контракт покупки оформляется отдельным use case / сервисным интерфейсом. Текущая реализация:

1. блокирует повторное нажатие;
2. эмулирует короткую асинхронную операцию;
3. записывает валидный subscription record;
4. только после успешной записи переводит session в `subscribed`;
5. показывает retry-friendly ошибку при сбое.

Такой контракт позволяет позже внедрить RevenueCat или StoreKit/Google Play Billing без изменения
экранов и навигации.

## 7. UI, доступность и адаптивность

- Safe-area учитывается на каждом полноэкранном маршруте.
- Интерактивные зоны имеют минимум 44×44 pt и accessibility role/label/state.
- Текст поддерживает разумное увеличение шрифта и не кодирует смысл только цветом.
- Тариф выбирается целиком нажатием на карточку; годовая скидка и итоговая цена видны явно.
- Дизайн-токены централизованы, стили вынесены из экранов в отдельные файлы при росте объёма.
- Клавиатура и системные inset не перекрывают основные действия.

## 8. Производительность

- Контекст разделяется на state/actions либо значение стабилизируется, чтобы действия не меняли
  identity на каждом render.
- Статические данные тарифов и конфигурация игры объявляются вне компонентов.
- `React.memo` применяется к карточке тарифа и другим повторяющимся leaf-компонентам.
- Callbacks стабилизируются там, где передаются memoized children.
- Игровая сцена разделена на memoized HUD, фон, дорогу, overlay и спрайты.
- Координаты, collision detection и transforms исполняются одним frame callback на UI runtime.
- React state меняется только на границах фаз; счёт не вызывает render всей сцены.
- Повторяющийся городской слой растрируется платформой и двигается только через transform.

## 9. Ошибки и наблюдаемость

- Повреждённая или неизвестной версии запись трактуется как отсутствие подписки без crash.
- Ошибка чтения приводит к безопасному anonymous-состоянию; ошибка покупки показывается в UI.
- В production не логируются пользовательские или платёжные данные.
- Для реального продукта добавляются crash reporting и аналитика событий воронки через адаптеры.

## 10. Проверки и критерии приёмки

Автоматически проверяются formatter, lint, TypeScript и тесты. Обязательные ручные сценарии:

1. чистая установка открывает onboarding;
2. «Продолжить» открывает paywall;
3. можно выбрать месяц или год, скидка года понятна;
4. покупка открывает home и защищена от двойного нажатия;
5. kill/relaunch сразу открывает home;
6. повреждённое local storage не приводит к crash;
7. интерфейс пригоден на малом экране и с увеличенным шрифтом.

## 11. Ограничения и дальнейшее развитие

Текущая подписка локальная и не защищена от изменения данных, что допустимо только для тестового
задания. Для production нужны реальный billing, server-side entitlement validation, restore
purchases, privacy/terms links, аналитика воронки, локализация, E2E-тесты и CI.
